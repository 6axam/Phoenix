# Kitty в Phoenix 1.1

Подробный сбор **выключен по умолчанию**. Phoenix не меняет `kitty.conf` и не включает управление Kitty самостоятельно. Без доступа к Kitty продолжает работать прежний fallback: обычное окно или один однозначно определённый локальный shell-каталог.

## Временная настройка для проверки

В пользовательской графической сессии создайте закрытый каталог и запустите отдельный Kitty:

```bash
install -d -m 700 "$XDG_RUNTIME_DIR/phoenix-kitty"
kitty -o allow_remote_control=socket-only \
  --listen-on "unix:$XDG_RUNTIME_DIR/phoenix-kitty/kitty.sock"
```

В Phoenix откройте «Настройки», включите сбор подробной структуры Kitty и укажите **абсолютный путь** к сокету, например `/run/user/1000/phoenix-kitty/kitty.sock` (подставьте свой UID). Либо передайте путь процессу Phoenix через `PHOENIX_KITTY_SOCKET`. Сокет и непосредственно содержащий его каталог должны принадлежать пользователю; каталог должен иметь права 0700. Временный каталог может потребоваться создать заново после входа. В настройках поле дополнительных сокетов принимает по одному абсолютному пути в строке. Для нескольких независимых процессов каждому нужен свой сокет, например `kitty-1.sock` и `kitty-2.sock` в этом каталоге; вместо GUI можно указать `"kitty_sockets": ["/run/user/1000/phoenix-kitty/kitty-1.sock", "/run/user/1000/phoenix-kitty/kitty-2.sock"]` в config.json, подставив свой UID.

`socket-only` разрешает контроль Kitty любому процессу с доступом к сокету, включая отправку команд и чтение терминала. Закрытый каталог защищает от других пользователей, но не от процессов того же пользователя. Эта команда меняет настройки только запускаемого экземпляра Kitty; Phoenix сам её не запускает. Режимы Kitty с паролем Phoenix пока не поддерживает: пароли не запрашиваются и не сохраняются.

Phoenix может собирать несколько независимых процессов Kitty: укажите основной сокет и дополнительные абсолютные пути в настройках (по одному в строке) либо массив `kitty_sockets` в config.json. Для каждого сокета проверяется PID через `SO_PEERCRED`: этому процессу должен соответствовать ровно один Kitty OS-window в Hyprland и один OS-window в ответе сокета. Адрес окна и PID используются только в момент сбора и не сохраняются как постоянные идентификаторы. Если один процесс содержит несколько OS-окон, подробные данные этого процесса пропускаются; другие однозначные процессы продолжают собираться. В Wayland `platform_window_id` может отсутствовать, поэтому Phoenix не угадывает соответствие.

## Архив текста

Отдельно включите «Архивировать текст терминала» в настройках. Это явный opt-in: в текст могут попасть **пароли, токены, переписка и другие личные данные**. Phoenix не умеет гарантированно распознавать секреты. Файлы защищены правами пользователя, но не шифруются. SQLite WAL, свободные страницы и резервные копии тоже могут содержать текст даже после его удаления из текущей базы.

Сохраняется текст, доступный Kitty через `get-text --extent all`, без ANSI-стилей. По умолчанию лимит — 32 МиБ несжатого текста на панель, 1 ГиБ сжатых уникальных блоков в базе. При превышении лимита панели сохраняется доступный хвост и выдаётся предупреждение; если превышен ограниченный бюджет входа или время запроса, панель пропускается. Доступность архива в плане проверяет факт записи; хеши и сжатие проверяются при чтении. На один проход сбора общий бюджет удерживаемого текста — 64 МиБ; при его исчерпании остальные панели пропускаются. Блоки сжимаются и дедуплицируются, их целостность проверяется; ротация снимков удаляет невостребованные блоки. Лимит архива не включает накладные расходы SQLite и резервные копии. При заполнении квоты новые панели могут быть пропущены.

В настройках можно задать лимиты и удалить архивы из текущей базы. Через CLI:

```bash
./phoenix.sh archive list latest
# Индексы окна, вкладки и панели в CLI начинаются с нуля:
./phoenix.sh archive show latest 0 0 0
./phoenix.sh archive purge --confirm
```

Для просмотра в GUI выберите снимок и нажмите «Архив терминала». Большие архивы в GUI показываются с ограничением первых 256 КиБ; CLI позволяет прочитать весь сохранённый текст. Управляющие символы фильтруются. Это исторический текст, не запущенный процесс. Удаление в Phoenix не очищает резервные копии и не гарантирует физическое стирание из SQLite/WAL или с носителя.

Необязательные исключения в `~/.config/phoenix/config.json`:

```json
{
  "kitty_exclude_panels": [42],
  "kitty_exclude_text": ["фраза-для-исключения"]
}
```

Первое — числовые Kitty panel ID **текущего процесса**, которые могут измениться после перезапуска. Второе — буквальные подстроки: при совпадении архив всей панели пропускается. Список оконных классов `exclude_classes` по-прежнему исключает Kitty целиком. Это не защита от всех возможных утечек секретов.

## Восстановление и проверка

1. Настройте сокет и включите подробный сбор. Для проверки архива отдельно включите сбор текста.
2. Создайте в тестовом Kitty несколько вкладок и панелей, откройте разные каталоги.
3. Выполните `./phoenix.sh snapshot --name "Kitty test"`, затем `./phoenix.sh inspect latest` и `./phoenix.sh restore latest --dry-run`.
4. В GUI откройте «Приложения» и выберите панели. План показывает зависимости и недоступные запущенные программы. Архив открывается отдельно и не передаётся shell.
5. В отдельной тестовой сессии закройте только тестовый Kitty и выполните восстановление. Повторите восстановление: Phoenix должен сопоставить открытое окно и не запускать его повторно.

Создаются новые shell-панели, расположение и активные элементы восстанавливаются по сохранённым layout и порядку. Точная геометрия и дерево splits, работающие программы, SSH-соединения и память процессов не восстанавливаются. Документированный session-интерфейс не описывает формат `set_layout_state`, поэтому Phoenix его не использует; доступные layout и порядок панелей сохраняются best-effort. Нельзя воспроизвести произвольные команды из снимка, даже подтвердив их: эти шаги помечены недоступными. Если окно уже открыто, его вкладки и панели не изменяются. При аварии после запуска повторное создание окна подавляется до проверки пользователем. Если в снимке или текущей сессии несколько окон Kitty и хотя бы одно уже открыто, Phoenix не может надёжно сопоставить их по классу и помечает восстановление Kitty как неоднозначное, не меняя эти окна. Журнал шагов: `./phoenix.sh recovery-log latest`.

## Миграция и возврат на 1.0

Диагностические команды `status`, `history`, `inspect` и `doctor` читают базу схемы 4 без миграции. Для использования новых возможностей остановите все работающие процессы Phoenix в данной пользовательской сессии: миграция проверяет блокировку daemon и наличие стандартно запущенного процесса, работающего с той же базой. Не запускайте одновременно Phoenix с разными XDG-каталогами состояния против одной базы. Программа не останавливает daemon сама.

При первом запуске с разрешением на запись Phoenix проверяет `integrity_check` схемы 4, создаёт отдельную резервную копию через SQLite Backup API, проверяет её целостность и версию и только затем транзакционно добавляет таблицы схемы 5. Копия хранится в `backups/migrations/schema4-*.sqlite3` внутри XDG DATA и не удаляется обычной ротацией. При ошибке или прерывании транзакция откатывается; до повторного запуска проверьте диагностическое сообщение и сохраните имеющиеся файлы базы вместе с WAL.

Код 1.0 не откроет схему 5. Безопасный возврат: остановите все процессы Phoenix; сделайте отдельную копию **всего каталога данных**, включая WAL, SHM и бэкапы; проверьте выбранную копию `schema4-*.sqlite3` через `PRAGMA integrity_check` в SQLite. Сначала запустите 1.0 на этой копии в отдельных `XDG_DATA_HOME` и `XDG_STATE_HOME`, убедитесь, что снимки читаются. Только затем при полностью остановленном Phoenix можно вручную заменить рабочую базу проверенной копией версии 4, предварительно сохранив текущую базу и её WAL/SHM отдельно. Архивы и снимки, созданные после копии, в старой базе отсутствуют. Не копируйте один только главный файл живой SQLite-базы; используйте SQLite Backup API.
